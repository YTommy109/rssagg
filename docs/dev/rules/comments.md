# コメント・ドキュメンテーション規約

プロダクトコードとテストコードの両方に適用する。behold の規約から、言語に依存しない部分だけを移植した。

## 書くこと

- 公開する関数・型には TSDoc（`/** */`）を日本語で付ける。非公開や自明なヘルパーは省略してよい
- コードの「なぜ（WHY）」を書く。「何を（WHAT）」は命名と型で伝える
- 非自明な判断・ワークアラウンド・制約がある箇所に、インラインコメントを付ける
- リファクタリングで型や関数を書き換えるとき、既存の TSDoc を削除しない。責務が変わったら内容を更新する

## 書かないこと

- コードをそのまま日本語に訳しただけのコメント（`// ファイルを開く` → `openFile()` で自明）
- タスク番号や変更履歴の参照。コミットメッセージに書く。テストの表示名（`it('...')`）にも書かない

## 壊れやすいコメント

書く前に「この記述は実装を変えたら書き換えが必要か」を自問する。必要なら WHAT を語っている。WHY だけ残すか、コメントごと削除して命名・型で表現する。

- **呼び出し順序・評価順序の断定**（「〜より前に評価される」）は、判定式を少し動かすだけで実物と食い違う。順序を語るなら、なぜその順序が必要か（不変条件・副作用の依存）だけを書き、書いた後に呼び出し箇所を読み合わせる
- **状態の断定**（「のみ」「常に」「〜のまま」）は、コードを変えた瞬間に静かに偽になる。残すなら、なぜその状態にするか（WHY）を主語にする（「internal のまま」ではなく「テストから呼ぶため internal にする」）

## 保守時の突き合わせ

振る舞い・状態・可視性を変えるコード変更をしたら、その挙動を説明している近接コメントと設計書・仕様書（`docs/` 配下）を、同じ diff 内で読み合わせて更新する。コードだけ直してコメントや仕様書を取り残すと、実装は正しいのに説明だけが古い誤りとして残る。

型・ファイルの追加・削除・リネームは、`docs/architecture.md` の図と構成表、および規約ドキュメント内のコード例・命名例との突き合わせも同じ diff 内で行う。歴史的な実例で削除済みの識別子を参照するときは、「旧 `〜`」と付けて現存しないことを明示する。

## テストコード

- テスト関数名で足りないときだけ、何を検証しているかを補足する
- Arrange / Act / Assert や前提条件を、日本語のコメントで区切ってよい
